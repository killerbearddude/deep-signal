## Code Commenting & Documentation Standard

### Purpose

Comments and documentation must help a future reader understand:

- **intent**
- **ownership**
- **assumptions**
- **invariants**
- **failure behavior**
- **deliberate exclusions**
- **design rationale**
- **refactor triggers**

Comments should preserve the reasoning that is not obvious from the code itself.

---

## 1. General rule

Prefer clear code first.

Use comments to explain:

> **Why this exists, why it is implemented this way, and what must remain true.**

Do **not** comment obvious syntax.

Bad:

```cpp
// Increment count.
++count;
```

Good:

```cpp
// Count completed simulation ticks, not rendered frames.
// Rendering may run multiple times between ticks.
++tick_count;
```

---

## 2. File-level documentation

Important files should begin with a short responsibility block.

Example:

```cpp
// simulation.cpp
//
// Responsibility:
// Applies deterministic simulation state transitions.
//
// Owns:
// - time advancement
// - production resolution
// - generated simulation events
//
// Does not own:
// - persistence
// - terminal or GUI output
// - player input
//
// Invariant:
// Given identical state and commands, simulation results must be identical.
```

This should let someone understand the file's role before reading the implementation.

---

## 3. Public type documentation

Important classes, structs, enums, and interfaces should explain their purpose and constraints.

Example:

```cpp
// Represents a colony's persistent simulation state.
//
// Colony contains state only. Cross-colony coordination and global
// economic resolution belong to the simulation layer.
struct Colony
{
    ...
};
```

Document important members when their meaning is not obvious:

```cpp
// Total processed structural material currently available.
// Must never be negative.
int structural_material = 0;
```

---

## 4. Function documentation

Document functions when they:

- modify important state;
- cross subsystem boundaries;
- enforce rules;
- have non-obvious preconditions;
- return results with important semantics.

Example:

```cpp
// Advances the game simulation by exactly one day.
//
// Preconditions:
// - state must already satisfy GameState validation rules.
//
// Effects:
// - advances the calendar
// - resolves colony production
// - updates stockpiles
// - generates corresponding events
//
// Does not:
// - save the game
// - print output
// - perform UI updates
//
// Returns:
// Events generated by this simulation step.
SimulationResult advance_day(GameState& state);
```

Do not create long documentation blocks for trivial accessors or self-explanatory helpers.

---

## 5. Invariants must be explicit

If a rule must always remain true, document it.

Examples:

```cpp
// Invariant:
// Resource quantities must never be negative.
```

```cpp
// Invariant:
// Every fleet location ID must reference an existing celestial body.
```

```cpp
// Invariant:
// Simulation code must not depend on persistence or UI services.
```

Important invariants should also be enforced in code/tests where practical.

A comment alone is not enforcement.

---

## 6. Document deliberate simplifications

This is especially important for incremental development.

Example:

```cpp
// v0.01 simplification:
// Structural ore has unlimited storage and no deposit depletion.
// This is intentional. Do not generalize the resource model until
// a later gameplay milestone requires those concepts.
```

This prevents future developers or AI agents from mistaking intentional simplicity for unfinished work.

---

## 7. Explain non-obvious design choices

When a reasonable developer could ask:

> "Why didn't they do this another way?"

leave the answer near the code or in a design note.

Example:

```cpp
// Keep simulation functions free-standing for now.
// There is currently no persistent engine-owned runtime state that
// justifies introducing a SimulationEngine object.
//
// Reconsider if shared simulation services or lifecycle state appear.
```

This is preferable to unexplained architecture.

---

## 8. Document boundaries

Subsystem boundaries should be obvious.

Example:

```cpp
// Persistence boundary:
// This repository converts GameState to durable storage.
// It must not implement gameplay rules.
```

or:

```cpp
// UI boundary:
// This panel may query simulation state but must not mutate domain
// objects directly. Changes must flow through commands.
```

These comments are highly valuable to future AI sessions because they prevent accidental architectural drift.

---

## 9. Document failure behavior

When failures matter, say what is expected.

Example:

```cpp
// Failure behavior:
// If the destination cannot be resolved, return an error.
// Do not silently move the fleet to a fallback location.
```

or:

```cpp
// Save failures must leave the previous valid save untouched.
```

This makes error-handling intent explicit.

---

## 10. Comment assumptions

Hidden assumptions create fragile systems.

Example:

```cpp
// Assumption:
// All values in this collection refer to the same simulation day.
// Mixing snapshots from different ticks would invalidate this calculation.
```

If the assumption changes later, the comment becomes a warning that the implementation must be reconsidered.

---

## 11. Comment temporary workarounds clearly

Use a consistent marker.

Preferred:

```cpp
// TODO:
```

for known future work.

```cpp
// FIXME:
```

for known incorrect or fragile behavior.

```cpp
// WORKAROUND:
```

for intentional temporary handling of an external limitation.

Each should explain **why**, not just what.

Bad:

```cpp
// TODO fix this
```

Good:

```cpp
// FIXME:
// This assumes one refinery per colony.
// Multi-refinery support will require selecting capacity by installation ID.
```

---

## 12. Do not leave misleading comments

A stale comment is worse than no comment.

When modifying code:

- update affected comments;
- delete comments that no longer describe reality;
- review nearby assumptions and invariants.

Documentation changes are part of the code change.

---

## 13. Prefer names over explanatory comments

Bad:

```cpp
int x; // amount of fuel needed for next jump
```

Better:

```cpp
int fuel_required_for_next_jump;
```

Use comments for semantics that naming cannot reasonably capture.

---

## 14. Explain units

Never leave important numeric units implicit.

Example:

```cpp
// Fuel consumption in units per simulated day.
double fuel_consumption_per_day;
```

or encode the unit in the name where reasonable:

```cpp
double range_km;
double duration_seconds;
```

Avoid unexplained magic numbers.

Bad:

```cpp
heat += 600;
```

Better:

```cpp
constexpr int kAfterburnerHeatPerTick = 600;
heat += kAfterburnerHeatPerTick;
```

and document the interpretation if needed.

---

## 15. Document ownership and lifetime when non-obvious

Especially in C++.

Example:

```cpp
// Non-owning reference.
// GameState owns all Fleet objects for the entire simulation tick.
const Fleet* selected_fleet;
```

or:

```cpp
// Owns the connection and closes it when the repository is destroyed.
std::unique_ptr<DatabaseConnection> connection_;
```

This is important when raw pointers, references, callbacks, or external handles are involved.

---

## 16. Document threading/concurrency assumptions

If applicable:

```cpp
// Threading:
// Called only from the simulation thread.
// GameState must not be accessed concurrently during this operation.
```

Do not assume future readers will infer concurrency rules.

---

## 17. Keep comments close to the code they constrain

Use:

- inline/file comments for local behavior;
- header documentation for public contracts;
- design docs/ADRs for architectural decisions affecting multiple files.

Do not hide important local assumptions only in a distant README.

---

## 18. Architectural Decision Records for significant choices

For larger decisions, create short records such as:

```text
docs/decisions/0003-simulation-remains-ui-independent.md
```

Suggested format:

```text
Decision:
Keep simulation independent of persistence and UI.

Context:
The game requires deterministic testing and multiple front ends.

Chosen approach:
Simulation receives state/commands and returns results/events.

Rejected alternatives:
Direct UI callbacks from simulation.
Database access inside simulation.

Reason:
Improves determinism, testing, and maintainability.

Revisit when:
Only if a demonstrated requirement cannot be supported through the boundary.
```

This is extremely useful for future AI-assisted work.

---

## 19. AI-oriented documentation rule

Write comments assuming a future AI model may inspect the repository **without access to the original conversation**.

Important comments should therefore make clear:

```text
What this code is for
Why this approach was chosen
What must not be changed casually
What assumptions are currently valid
What complexity has been deliberately deferred
```

Do not write comments that depend on chat context such as:

```cpp
// We discussed this earlier.
```

Instead write the actual reasoning.

---

## 20. Review standard

Before accepting a substantial change, check:

- Is the code itself clearly named?
- Are important responsibilities documented?
- Are invariants explicit?
- Are assumptions documented?
- Are units clear?
- Are deliberate simplifications identified?
- Are subsystem boundaries preserved?
- Are TODO/FIXME comments specific?
- Did the change make any existing comments stale?
- Could a competent developer or fresh AI session understand **why** this code exists?

---

## Short version for project instructions

If you need a compact version to paste into an `AGENTS.md` or project instruction:

> **Documentation Standard:** Treat comments and documentation as part of implementation quality. Write clear code first; comments must explain intent, ownership, assumptions, invariants, failure behavior, deliberate simplifications, architectural boundaries, design rationale, and refactor triggers rather than restating syntax. Document important files, public types, state-changing functions, units, ownership/lifetime, and non-obvious constraints. Mark TODO, FIXME, and WORKAROUND items with specific reasons. Keep comments current whenever code changes. For major architectural choices, record a short decision note describing context, chosen approach, rejected alternatives, reasoning, and conditions for reconsideration. Write documentation so a future developer or AI agent with no chat history can reconstruct what the code is meant to do and why it is designed that way.
